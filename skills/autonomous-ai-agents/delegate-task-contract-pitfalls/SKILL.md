# delegate_task 契约陷阱

## When to Use

- 用 `delegate_task` 派发子 agent 时(尤其带 `output_schema`)。
- 把一件大工作拆给多个子 agent 并行时。
- dispatch 「什么都没发生」或报出你从没写过的结构时。

`delegate_task` 有两个字段会在**派发前**静默吃掉整次 dispatch:错误的 `output_schema`,以及
重叠的写集合。两者都不会报「任务失败」,只是什么都没发生。

## 1. `output_schema` — `required` 是扁平的字段名数组

校验发生在派发之前。写错的代价是一整个 round-trip 且什么都不会跑,而报错信息里会出现一个
你从没写过的嵌套结构。

```jsonc
// 错 —— required 把名字又包了一层数组
"required": [["a", "b"]]   // -> {'item': ['a','b']} is not of type 'array'

// 对
"required": ["a", "b"]
```

这个错误容易连续犯,因为直觉模型是「required 列出若干项,每项又有自己的字段」。不是。
看到报错说 `{'item': [...]}` 就是多写了一层数组。

**批量提交时 `required` 里不能只放一部分字段名。** 这条 JSON Schema 默认
`uniqueItems: true`,所以 `["a", "b"]` 会被当作「一个由两项组成的元组」去校验。
更隐蔽的是部分项会被改写成 `{"item": [...]}` 之外的样子而**不报错** —— 于是
整个 batch 静默回滚,只有一条 warning 提到 `batch aborted, all touched skills
rolled back`。**看到这条 warning 就是漏项了,不是某个 op 的内容有问题**,
不要去逐个 op 找错。

**被拒后的升级顺序 —— 第一次被拒就删掉整个 `output_schema`**,不要先试着修形状:

`output_schema` 的收益远小于它的风险。写对了只是让汇报更整齐;写错了是**整次派发
一个子 agent 都不跑**,而你为它花掉的每个 round-trip 都在浪费用户的等待。已经踩过时
(连续两次修形状、第三次才放弃)说明直觉层对 JSON Schema 序列化不可靠 —— 那就换成
不需要它的方案,而不是继续赌第四次。

具体做法:把汇报契约写进 `goal` 的散文里,例如
「用散文汇报:改了什么、哪些验收项你实测 PASS、哪些没做及原因」,然后**删掉
`output_schema` 键**。子 agent 交回有用的散文,好过一次根本没跑起来的派发。
**不要让汇报上的讲究挡住正事。**

## 2. 并行拆分 —— 按「不相交的文件集合」拆,不要按任务阶段拆

两个子 agent 能并行,**当且仅当它们的写集合不可能重叠**。安全的轴是**文件集合**,不是
「迁移」vs「声明」这种阶段划分:一个被要求「只声明类型、不要动 impl 文件」的 agent,
仍然需要那个 impl 文件在它工作期间能编译通过 —— 于是两个 agent 互相看见对方改了一半的
文件,在 `cargo check` 上赛跑。

**步骤:**

1. 枚举这次工作会碰的**每一个**文件。
2. 把这份列表切成互不相交的集合,一个子 agent 一个集合。
3. 把每个 agent 的集合写进它 `context` 里的**白名单**,并点名「另一个 agent 拥有哪些文件」,
   让它知道要躲哪些。
4. 当一个 agent 要消费另一个 agent 声明的类型时,按**声明点 vs 使用点**切
   (enum.rs / struct.rs / const.rs 的声明归一个,impl.rs / fn.rs 的迁移归另一个)。
   这是不相交文件,所以安全 —— 同时给「只声明」的那个 agent 一句明确的
   「不要为这些类型写任何 impl block」,防止它闯进消费者的半边。
5. 事后验证:`git status --short` 只能出现各集合的并集。

需要自己集合之外文件的 agent 应该**上报需求,而不是自己去拿那个文件**。

### 2a. 修好一个缺陷后，不要同时派第二个 writer 修相邻的东西

修完一组后，你手上通常同时浮着两类待办：**已经定位到根因的**，和**你怀疑但没证据的**。
把它们打包进「下一轮」一起派出去，看起来高效，实际是同一个坑：第二个 writer 的
根因描述来自你一方的读数，而那一方的读数本轮已经被证伪过。

真正发生过的链条：先派 A 修「楼梯上不去」，读数支持；随后又派 B 修同一处楼梯并
附带另外两组。A 落地时 B 已经在改同一棵树，B 的一组改动被 A 抢先提交、混进了
A 的 commit，而 B 真正要修的那条在 A 的 commit 之后变成了重复劳动。发现时
`git log` 里有两组无关内容挤在一个 commit 里，只能靠第二个 agent 自己说
「它先一步把我的改动混进去了」才拼出真相。

**派单前先把待办分成两堆：**

| 堆 | 判据 | 怎么派 |
|---|---|---|
| 已确证 | 逐帧读数连续、gaps=0、两个独立测量一致 | 一个 writer 全部接掉 |
| 待证实 | 读数来自单次运行、或判据源码没看过 | 先派只读 agent 复现，**不要进 writer 批次** |

如果两堆都急，**先派只读的**。只读 agent 不会污染 commit，它的产出（可核验的
读数 + file:line）恰好是 writer 最需要的输入。反过来做，就要准备好事后拆分
别人 commit 的代价。

**已提交的修复要先落地再派下一个 writer。** 「等 A 跑完就派 B」不等于「串行」：
A 交付前 B 就已经启动。派 B 之前先确认 A 的 commit 已落盘
（`git log --oneline -1` + `git status --short` 干净），并把 A 的 commit hash
写进 B 的 context，让 B 先 `git diff HEAD` 看自己还需不需要动同一段。

### 2b. 「一份源 × N 个 locale」的翻译类任务 —— 按**源文件**切,不按语言切

把同一个源文件翻成 N 种语言,写出集合是 N × 源文件数。此时**切分轴必须是源文件**,
一个源文件(及其全部语言版本)永远归同一个 agent。按语言切(一个 agent 翻全部 en、另一个
翻全部 ja)看着更均衡,实际更糟:N 个 agent 同时读同一批源文件、各自重建翻译上下文,
术语在语言之间漂移,而且 N 个 agent 都可能想在同一份「术语表」文件上落笔。

在每个 agent 的 context 里写死这个乘积,让它自查:

```
FILES TO CREATE: 12 source files x 4 locales = 48 target files
```

同时把**不能翻的东西**逐条点名,这是这类任务真正会翻车的地方:

- LICENSE / 法律文本 —— 逐字节复制,**明确说「不翻译」**,否则模型会「顺手润色」
- 密码门控值(`password: <value>`)与 keywords meta —— 原样复制,改了会锁页
- frontmatter 的 **key 集合**不许增删改名,只翻 value;`order:` 等保持源值
- 代码块、数字、标识符、命令行跨语言逐字节一致
- 文档骨架(标题层级序列、表格、告警块)不许因翻译而改变

## 2c. 用户说「派 N 个子 agent 验证」时，先分清是写还是读

用户常把「修完派 N 个子 agent 多开无头浏览器截图验证」当成一条完整要求。但这句话
里的 **N 是对验证阶段的约束，不是对修复阶段的**。如果直接把 N 路修复也并行派下去，
N 个 agent 会同时写同一批源文件——`delegate_task-contract-pitfalls` §2 的失败模式。

**先做一次写集合勘查，再决定拆分轴：**

```bash
find src -name '*.rs' -exec wc -l {} + | sort -rn | head -20
grep -c "fn " src/<biggest>.rs
```

看到**单个文件就占了源码的 30%+**（`game.rs` 一家 8369 / 22511 行），而用户的多个
bug 横跨同一批文件时，**修复阶段就是串行的**，N 路的价值在验证。

**分阶段派发：**

| 阶段 | 并行度 | 理由 |
|------|--------|------|
| 修复 | 1 个 agent | 写集合重叠，按不相交轴拆不开 |
| 验证 | N 个 agent | 只读（截图 / 读日志 / 跑探针），无撞车风险 |

派发时把这个理由**写进给用户的回复**（而不只是默默按串行做）：用户看到的是「为什么
没按 8 路并行」，一个带勘察数据的解释比沉默的执行更可信。

**勘查要在派单前做，并且报数字。** 「`game.rs` 一个文件 9270 行，占全仓 37%，
你报的 5 类问题全都要动 `game.rs`/`player.rs`/`camera.rs`/`const.rs`」比
「因为会有冲突所以串行」有说服力得多。用户接受的是有依据的偏离，不是未经勘查的
自作主张。

**「N 个 agent」这句话本身有歧义，先分清是写还是读。** 用户说「派 N 个子 agent」
时可能指整个任务，也可能只指验证环节。**不要默默按自己的理解执行**——用一句话
说清你的解读并给出依据（「N 路我用在验证阶段，因为写阶段按文件集合拆不开」）。
这一句是防止用户以为你少派了 agent 的唯一保险。

**循环的终止条件要提前说清。** 「循环直到完美对齐」如果不给终止判据，会变成
无限循环或无限期拖延。可用的终止条件：完整一轮全绿，或者剩余失败项**全部**被判定为

**验证阶段的 context 必须写死端口与 profile 目录**（`delegated-result-verification`
§17：并发子 agent 会互相杀死对方的 debug 端口和临时 profile，看起来像应用坏了）：

```
每个 worker 独占 BASE_PORT=9300+{index}，user-data-dir 写死到 /tmp/vcw-verify/p{index}。
9231-9236 已被 tools/verify-parallel.sh 占用，不要碰。
```

**验证阶段的验收只能是感知检查，不能是数字闸门。** stddev / 三角形数 / console 无报错
对「渲染出来的东西是不是人看的东西」毫无判断力（`delegated-result-verification`
§9）。要求 worker 用 `vision_analyze` **描述图里到底有什么**，并明写：

```
禁止用 "stddev > 0" / "HTTP 200" / "console clean" 作为验收。
必须加载图片并用文字描述你看到什么：角色朝向、车辆是否完整、地图是否延绵。
```

### 2d. 子 agent 提交时，**「分开提交」必须逐 commit 验收

派单时写「先单独 commit 掉 WIP，升级改动另起一个 commit，不要混在一起」——
子 agent **很可能照做一半**：它会 `git commit -a` 一次把暂存区连同新改动一起打包，
生成一个 `chore(deps): bump X` 却含 11 个文件 / +954/-493 的 commit。message 写得
越认真，越像已经分了类，**但 message 不改变实际内容**。

**唯一的验收方式：逐 commit 读 `--numstat`，和你在派单里声明的分组逐行对照。**

```bash
git log --oneline -3
for c in <sha1> <sha2> <sha3>; do
  echo "--- $c $(git log -1 --format=%s $c)"
  git show --numstat --format='' "$c"     # 文件 + 行数，必须落在该 commit 声明的集合内
done
```

判断标准：**一个 commit 的文件清单是另一个 commit 的超集 = 没分开。**
message 里写了「规范整改」「顺带修复」不算分开 —— 那是同一个 commit 里
三类互不相关的东西，需要三次 commit。

**派单时把分组写成可核对的清单**，不要只写「分开提交」：

```
commit A `feat(interior): …`   ← collision.rs const.rs game.rs interior.rs player.rs
commit B `fix(test): …`        ← render.rs（仅两处围栏）
commit C `chore(deps): …`      ← Cargo.toml Cargo.lock lib.rs
```

子 agent 遇到分组里没列出的文件（例如派单时漏掉的 `lib.rs`），正确做法是
**在报告里点名并说明归到哪**，而不是默默塞进最接近的那个 commit。

**同时在跑的第二个 writer 会把你的分组吃掉。** 即使你逐条写明分组，另一个
writer 抢先 commit 时会把你的改动一并 stage 进去，产出一个含两组无关内容的
commit；事后只能靠 `--numstat` 发现，发现后**不要让它改写别人的 commit**，
先问清哪几行属于谁，再决定是接受合并（写进报告）还是历史重组。

### 2i. 已经在主 agent 手里的事实，必须随派单一起交出去 —— 否则子 agent 会用整个预算重新推导一遍

子 agent 跑满预算、只读文件、一行代码没写，最常见的原因不是它笨，而是**你已经知道答案却没写进 context**，于是它把预算花在了「先搞清楚这个 API 怎么用」上。你已经查过的东西（读过源码、grep 过、编译验证过、踩过坑确认过）对它是净信息成本。

**派单前先问三句话，任何一句是「是」就必须把它写进 context：**

1. 我是不是已经读过相关源码 / 看过官方文档？
2. 我是不是已经实测过某个行为（编译过、发过请求、看过真实输出）？
3. 我是不是已经踩过一个坑，知道某个方案走不通？

答「是」的每一条都要落成 context 里的一行字。**格式是「事实 + 出处 + 让它复核而不是照抄」**：

```
- `Server::route` 是同步且可链式，签名在 `core/src/server/impl.rs:415`：
  `pub fn route<S>(&mut self, path: impl AsRef<str>) -> &mut Self`。
  不要写 `.await`（旧文档说 async，已过时）。这是我核对的，请你去源码复核一眼。
```

末尾那句「去复核」很重要：它把「照抄」变成「交叉验证」，既省了预算又保住了正确性。

**已经在 context 里给全 API 事实时，还要显式禁止它再推导一遍：**

```
框架 API 面已经映射完毕，见上。不要重新推导，直接写代码并频繁编译。
```

这一句能显著改变它的行为分配。没有它，子 agent 仍会把大半预算花在「再确认一遍」上，因为它的默认倾向是「先理解系统再动手」。

**反过来：主 agent 自己没查的事实，不要替它下结论。** 可以给它方向和命令（「去 `~/code/<crate>/tests/` 看有没有现成 e2e harness，直接抄那个模式」），但结论要它自己读出来并报 file:line。区分「我知道的事实」和「我怀疑的事实」，前者交出去，后者派只读任务。

**给建议前先过一遍规则原文。** 你为了绕开一个命名冲突而建议的写法，本身可能正好违反另一条规则（本例：建议 `use x::{Error as Alias}` 绕开同名冲突，而 §6.5 明令禁止 import 里的 `as` 重命名 —— 子 agent 照做，规则从 51/51 掉到 45/51）。派单时给的每一条具体写法，都是你替它做的规则判断，**先 grep 一次规则原文再给**。

### 2h. 派「收窄 / 清理」类任务,brief 的偏向词就是交付量

brief 里写「存疑就保留(in doubt → leave as-is)」,子 agent 会在**每一处**存疑点选择保留 —— 首波交付必然偏保守,用户随即指出「还有很多没改」要求第二波。收窄类任务(可见性 `pub`→`pub(crate)`、提常量、删 dead code)的正确写法是把**默认动作**写成断言句,把例外交给编译器点名:

```
默认动作 = 收窄。只有编译器 E0603/E0624 点名外部消费者、或 tests/ 引用,才恢复/保留。
grep 零外部引用而你不确定 = 收窄,让 cargo check 裁决 —— 不确定不是保留的理由。
```

同时把会反咬的硬约束一并写进 brief(如有):例如「零读者 item 收窄会触发 dead_code warning 而 `#[allow]` 被禁」—— 这类 item 只能单独汇总上报等拍板,**不许沉默保留、也不许沉默收窄**,否则 agent 遇到时一定会自作主张选一边。

### 2g-b. 用现成模板起项目：模板带的不是脚手架，是上游的默认决定

从 template/quick-start 仓库起商业项目时，先把模板当成**未经审阅的第三方代码**读一遍，
尤其是这些默认会在第一次 push 就生效的地方：

- **CI 发布工作流**。模板常带「master 上自动 publish 到 crates.io + 自动建 Release」的
  job。私有商用仓库直接沿用，第一次推 master 就把源码公开发布出去了。
  `ls .github/workflows/` 逐个看 job 名含不含 `publish` / `release`，含就删或改成私有的。
- **包名与仓库 URL**。模板的 `[package].name` 和各 manifest 的 `repository` 仍指向上游，
  会在 Cargo.toml、docs.rs、badges 上留下错误归属。
- **README 整段是模板的自我介绍**（宣传的是被依赖的那个库，不是你的项目）。
- **上游遗留的规范债**。模板通过你这套 audit 只是因为 `git diff` 拿不到基线（见
  `verifying-against-a-real-gate`「An empty diff window」），一旦推上基线就会全部显形。

**规则：模板落地后、派任何 worker 之前，先跑一遍全套 gate 拿到真实基线数字**，
再决定这些继承债是自己清还是让 worker 清。带着「当前是 51/51」的错觉开工，后面每次
新增代码都会把分数压下去，看起来像在退化。

### 2g-c. 多端并行时先落一份契约文档，再派任何 writer

后端 + 前端 + 第三方客户端并行开发时，最大的浪费是双方各自猜对方的 payload。
先写一份 `docs/api-contract.md`：每个端点的路径、请求体、响应体、错误码、
**并明确写出无法表达在类型里的约定**（绝对 URL vs 相对路径、字段是否可能为 null、
某个字段是否总是存在）。

几个只有在并行中才会暴露、必须提前钉死的点：

- **上游库的能力边界要先实测，再写进契约**。本例：multipart 解析器存在于框架的
  工作树里，但没发布到 crates.io —— 本项目锁定的版本根本没有那个 API。照着工作树写
  契约，等于写了一份编译不过的契约。验证方法是把**实际解析到的依赖目录**列出来看，
  而不是看框架仓库的源码目录。
- **同一份契约要同时喂给前端和后端的 context**，并且**任何一方提出契约缺口时，
  改契约本身再广播**，不要让某一侧私下适配。两个 worker 各按自己理解写出来的东西，
  在集成时才暴露，成本是整轮返工。

**规则：契约文件的每次变更都要显式 steer 给所有在跑的 worker**，
并写清「改了哪一节、为什么、从现在起按新契约」。前端 worker 自己发现的契约缺口
（缺 `isAdmin`、示例与正文矛盾）是高价值信号 —— 接住它，改契约，别让它自己绕过。

### 2e. 发现被污染的 commit：只拆历史,不碰代码

一个 commit 已经落地且混入了不该有的内容时，正确的补救是
**纯历史重组**，代码字节一个都不能变（见 `git-standards` §3.8 的树哈希自证）。
派单时必须写死「不改任何代码内容」，否则子 agent 会顺手把「反正要改」一起改了，
你就失去了「拆分前后字节一致」这个可验证基线。

### 2f. 子 agent 假完成后的重派：先替它答掉它正要查的问题

一个子 agent 跑了十几二十次工具调用、**零改动零 commit**，最后一句话是
「Let me check X and how Y happens」——将来时。这是 §7 之外的第二种假完成形态：
它不是放弃了，是**预算烧在了读文件上，计划本身是对的**。

**重派时不要把原 goal 原样再发一遍。** 那样新 agent 会重走同一条读文件的路。
正确做法有两条，都要在自己的会话里先做：

1. **自己把那个问题查掉，写进新 goal 的 context。** 子 agent 正要问的那个问题，
   正是它计划的下一步；你替它答掉，等于把它 20 次调用的预算直接省下来。
   答的时候要连 `file:line` 一起给，并且**要求它去验证而不是接受**——
   「这是我查到的链，去复核」比「照我说的改」可靠得多。
2. **按优先级重排，并显式授权它只做前面几项。** 一口气派五类异质缺陷，
   agent 会均匀地把预算摊开然后每一项都做一半。改成
   `P0-A / P0-B / P1 / P2` 排序，并明写
   「只能做前两个就只做这两个，明确说 P1/P2 没做，不要为凑齐报告把没做的写成做了」。

重派时还要在 context 里点明上一次失败的事实，让它知道时间预算被重新分配过：
「上一次派发跑了 N 次调用、零改动、最后一句停在『Let me check …』」。

### 2g. 派去**修验收工具**的 agent，必须明写「宁可 SKIP，不要假 PASS」

修应用的 agent 会为了让读数对上而改判据；**修 harness 的 agent 会为了让 suite 变绿
而降低判据**，而这比红色更危险 —— 它让你以为验证过了。

派这类任务时把纪律写进 goal：

```
判据错了要改判据；判据没错而应用有问题，才是缺陷。
不确定的读数标 SKIP 并写明为什么缺证据，禁止标 PASS。
禁止为了让总数好看而放宽门限 —— 收紧门限导致新 FAIL 是正确结果。
```

同样明确：**禁止改 `src/`**。应用已修完，harness 是来量它的，不是来让它的读数好看的。
在 goal 里点名写死禁止目录，并说明应用侧已完成（commit 数 / 测试数 / HEAD）作为基线。

**读出「判据本身结构上不可能通过」是最有价值的产出。** 一个把前向写成
`(-sin yaw, -cos yaw)` 而源码是 `[cos yaw, -sin yaw]` 的方向检查，点积恒为 0，
永远 FAIL —— 它把正确行为判成 FAIL。派单时明说「区分三类：应用缺陷 / harness 判据错 /
harness 自身崩」，并要求给出 file:line 证据。修完让 worker 报
`N pass / N fail / N skip` 的**三态**分布（不是二态），SKIP 必须写明缺什么证据。

## 3. 验收

```bash
git status --short              # 改动只能落在各 agent 的白名单并集内
```

子 agent 声称的每个验收项,主 agent 独立复测 —— 子 agent 的总结是**自述**,不是事实。
「N 个源文件 × M 个语言」这类乘法任务尤其要点名核对:用脚本枚举期望路径集合与实际落盘
集合求差集,不要靠目测 `git status` 的行数。

### 3a. 主 agent 写给子 agent 的简报里,版本号和 flag 列表是**假设**

派发简报时你手里的事实(如「默认模型是 X」「有 N 个 resource」)通常来自记忆或上一版文档,
可能已过时或漏项。**子 agent 实跑一遍的结论比简报可靠**,因为它有执行证据而你没有。
它报出与简报冲突的项时,**默认它对**,并在给用户的最终汇报里把纠正后的值写清楚 ——
尤其是当简报本身就是你转述的旧文档时,静默接受简报错误等于把错误又写回文档一遍。

派发时就写明:「以下默认值/flag 列表请逐条实跑复核,不要相信本简报;有冲突以你的实测为准,
并在报告里点名」。

### 3b. 派发单元完成后仍可能在写 —— 收尾时先确认没人还在动

子 agent 的“完成”消息到达时,其他并行单元(尤其先后派发的第二批)可能还在写文件。
**在 commit 前按 mtime 甄别,不要靠 `git status` 的文件列表判断所有权**:

```bash
stat -f "%Sm  %N" -t "%H:%M:%S" <所有 modified 文件>
```

晚于你最后一次写文件时间的,是别人的在途改动。**共享工作树里永远不要 `git add -A`** ——
只 `git add <精确路径列表>`,并在 commit message / PR body 里写明排除了哪些文件及原因。

### 3c. 被 stop / kill 的子 agent 会留下 stale `.git/index.lock`

并行子 agent 在 git 写操作中途被终止,会留下 `.git/index.lock`,之后**所有** git 写操作报
`File exists`。**确认陈旧再删**,三个条件必须同时满足:

```bash
ps -ax -o pid,comm | grep -E 'git' | grep -v grep   # 查不到 git 进程
lsof .git/index.lock                                 # 查不到持有者
stat -f "%Sm" -t "%H:%M:%S" .git/index.lock           # 明显早于当前时间
```

删前 `cp .git/index /tmp/index.bak`;删后用 `git ls-files | wc -l` 校验索引完好。
**不要因为报错就条件反射地删锁** —— 真有另一个 git 在跑时删掉会损坏索引。

```bash
git status --short              # 改动只能落在各 agent 的白名单并集内
```
